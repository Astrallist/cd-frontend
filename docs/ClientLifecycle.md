# Жизненный цикл клиента, сессий и сетевых вызовов

Этот документ описывает фактический контракт браузерного клиента FunCards с
сервером и правила, которым должен следовать клиент при управлении состоянием.

Клиент запускается как Blazor WebAssembly приложение. Он не является источником
истины для игры: отображает серверное состояние, отправляет намерения игрока и
применяет полученные от сервера изменения.

## Виды сессий

В приложении существуют три независимые сущности, которые не следует смешивать.

| Сущность              | Место жизни                        | Создание                        | Завершение                                             |
|-----------------------|------------------------------------|---------------------------------|--------------------------------------------------------|
| Сессия авторизации    | Браузер и хранилище сессий сервера | Успешный вход или регистрация   | Logout, `401`, очистка локального токена               |
| Realtime-подключение  | Одна вкладка браузера и SignalR    | После подтверждения авторизации | Logout, неавторизованное подключение, закрытие вкладки |
| Игровая сессия (матч) | Память сервера                     | Запуск заполненного лобби       | Завершение матча                                       |

### Сессия авторизации

Токен хранится в `localStorage` по ключу `funcards.session`. В памяти клиента
`SessionState` хранит токен, текущего пользователя и признак завершённой
инициализации.

Состояния:

```text
Не инициализирована -> проверка localStorage -> анонимный пользователь
                                           `-> проверка /api/auth/me -> авторизован
                                                                        `-> анонимный
```

На старте приложения клиент читает токен. Если он есть, вызывает
`GET /api/auth/me`. При успехе сохраняет пользователя в памяти; при `401`
удаляет локальный токен и переходит в анонимное состояние.

После `POST /api/auth/login` или `POST /api/users` сервер возвращает токен и
пользователя. Клиент сохраняет токен в `localStorage` и устанавливает
пользователя без дополнительного запроса `/api/auth/me`.

Защищённые HTTP-запросы содержат заголовок:

```http
X-FunCards-Session: <token>
```

Любой обычный API-вызов, получивший `401`, должен завершить локальную сессию.
Исключение: login, registration и logout не должны пытаться повторно завершать
сессию по своему `401`.

При явном logout клиент сначала вызывает `POST /api/auth/logout`, затем в любом
случае очищает локальные токен и пользователя. После этого realtime-соединение
должно быть закрыто, а локальные лобби и сведения о матче — сброшены.

### Realtime-подключение

Авторизованный клиент открывает одно SignalR-подключение к `/hubs/game`. Для
аутентификации используется `AccessTokenProvider`; при WebSocket SignalR может
передать токен серверу как параметр `access_token`.

Подключение не следует открывать для анонимного пользователя. При успешном
подключении клиент обязан запросить актуальные лобби и наличие текущего матча:

1. `GetLobbies`;
2. `GetCurrentGame`.

Состояния подключения:

```text
Нет подключения -> Connecting -> Connected
       ^                 |             |
       |                 v             v
       +----------- Disconnected <- Reconnecting
```

Сетевые ошибки обозначают состояние недоступности backend. Повторы выполняются
с задержками 5, 15 и затем 30 секунд. HTTP-восстановление проверяется через
`GET /health`; realtime-восстановление открывает новое подключение только для
авторизованного пользователя.

После любого SignalR reconnect создаётся новый `ConnectionId`. Поэтому клиент
должен считать старую реплику игры устаревшей и выполнить следующий алгоритм:

1. вызвать `GetLobbies` и `GetCurrentGame`;
2. если матча нет — очистить локальную игровую реплику;
3. если матч есть — вызвать `JoinGame`, чтобы вступить в группу нового
   подключения;
4. запросить и применить новый `GetGameSnapshot`;
5. только после этого принимать последующие уведомления и patch-и.

Это существенно: членство SignalR в группах привязано к соединению, а не к
пользователю. Повторное подключение без `JoinGame` перестанет получать
`GameChanged` для матча.

### Игровая сессия

Игровая сессия принадлежит серверу и существует только в памяти. Клиент хранит
лишь её реплику (`StateSyncClient`) и не может локально определять результат
действия.

После запуска матча сервер связывает обоих игроков с игровым runtime. Пока
матч активен, глобальная навигация должна принудительно держать игрока на
маршруте `/game`: переход на другую страницу не завершает матч.

При окончании матча сервер рассылает `GameFinished`, удаляет игровой runtime и
снимает у игроков признак активного матча. Клиент показывает результат, очищает
временный UI-состояние игры и после подтверждения игрока возвращается на
главную страницу. После `GameFinished` нельзя пытаться получить snapshot или
patch-и завершённого матча.

## Лобби и запуск матча

В текущем UI интерактивные операции лобби выполняются через SignalR, а не через
HTTP. Перед созданием или входом игрок выбирает допустимую колоду.

Hub-методы:

| Метод                                  | Когда вызывать                            | Результат                   |
|----------------------------------------|-------------------------------------------|-----------------------------|
| `GetLobbies`                           | После подключения и для обновления списка | Полный список лобби         |
| `CreateLobby(CreateLobbyRequest)`      | Игрок создаёт ожидание соперника          | Новое лобби                 |
| `JoinLobby(lobbyId, JoinLobbyRequest)` | Игрок входит в открытое лобби             | Обновлённое лобби           |
| `LeaveLobby(lobbyId)`                  | Не-владелец выходит из ожидания           | Лобби обновлено или удалено |
| `DisbandLobby(lobbyId)`                | Владелец удаляет ожидание                 | Лобби удалено               |
| `StartGame(lobbyId)`                   | Владелец запускает заполненное лобби      | `GameStartedDto`            |
| `GetCurrentGame`                       | После подключения, reconnect и навигации  | Есть ли активный матч       |

Серверные push-события:

| Событие                   | Действие клиента                                           |
|---------------------------|------------------------------------------------------------|
| `LobbiesChanged(lobbies)` | Целиком заменить локальный список лобби                    |
| `GameStarted(started)`    | Установить признак активного матча и перейти на `/game`    |
| `GameChanged()`           | Забрать накопленные patch-и через `GetGamePatches`         |
| `GameFinished(finished)`  | Показать победу/поражение и прекратить синхронизацию матча |

Ожидающее лобби удаляется на сервере, когда закрылось последнее SignalR-
подключение пользователя. Отключение не завершает уже запущенный матч.

## Синхронизация состояния игры

При открытии `/game` клиент должен:

1. обеспечить активное SignalR-подключение;
2. проверить `GetCurrentGame`;
3. вызвать `JoinGame` для вступления в группу матча;
4. запросить `GetGameSnapshot`;
5. полностью заменить локальную модель snapshot-ом;
6. начать обрабатывать `GameChanged`.

Вступление в группу и получение snapshot надо организовать без окна потери
обновления. Практический вариант: вступить в группу, получить snapshot, затем
сразу получить `GetGamePatches`; при ошибке версии повторить snapshot.

`StateSync` имеет сервер как единственный источник истины:

- snapshot заменяет весь корень локальной модели и устанавливает её версию;
- каждый patch применяется строго в порядке выдачи и только если
  `fromVersion` совпадает с локальной версией;
- после успешного patch локальная версия становится `toVersion`;
- при пропуске версии, дубликате, невалидном пути, неверном типе или ошибке
  разбора клиент обязан отбросить реплику и получить новый snapshot;
- сервер может выдать разные проекции двум игрокам; клиент не должен сохранять
  или восстанавливать скрытые карты из старой проекции.

Когда приходит `GameChanged`, это не payload состояния, а уведомление о его
наличии. Клиент сериализует загрузку patch-ей (например, через `SemaphoreSlim`)
и вызывает `GetGamePatches`. После успешной игровой команды он также сразу
забирает patch-и, не ожидая доставки push-события.

## Игровые команды

Все команды матча вызываются через `/hubs/game` и возвращают
`GameActionResult`. При `Success: false` клиент показывает причину отказа и не
меняет авторитетную модель локально.

| Метод                                                                 | Назначение                                                        |
|-----------------------------------------------------------------------|-------------------------------------------------------------------|
| `PrepareCardPlay(cardId)`                                             | Получить обязательные запросы выбора целей перед розыгрышем карты |
| `PlayCard(cardId, targetCellId, declaredTargetIds, targetSelections)` | Разыграть карту с выбранными целями                               |
| `Pass()`                                                              | Передать приоритет или разрешить стек                             |
| `ReplaceMulliganCard(cardId)`                                         | Заменить карту в mulligan                                         |
| `FinishMulligan()`                                                    | Подтвердить руку после mulligan                                   |
| `ChooseTriggerTargets(stackItemId, targetIds, declined)`              | Ответить на выбор целей триггера                                  |
| `Concede()`                                                           | Сдаться                                                           |

Подготовка целей не является изменением матча. Окончательный выбор передаётся
в `PlayCard`; сервер всё равно проверяет допустимость действия и целей.

## HTTP API

`FunCardsApiClient` использует HTTP для аутентификации, CRUD-данных и проверки
доступности сервера.

| Назначение       | Маршруты                                                                                                                             |
|------------------|--------------------------------------------------------------------------------------------------------------------------------------|
| Доступность      | `GET /health`                                                                                                                        |
| Авторизация      | `POST /api/users`, `GET /api/users/{username}/exists`, `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/me`           |
| Карты и правила  | `GET/POST /api/card-templates`, `GET/PUT/DELETE /api/card-templates/{id}`, `GET /api/deck-construction-rules`, `GET /api/card-texts` |
| Наборы карт      | `GET/POST /api/card-sets`, `PUT/DELETE /api/card-sets/{id}`                                                                          |
| Колоды игрока    | `GET/POST /api/decks`, `GET/PUT/DELETE /api/decks/{id}`                                                                              |
| Стартовые колоды | `GET/POST /api/admin/starter-decks`, `PUT/DELETE /api/admin/starter-decks/{id}`                                                      |
| Локализация      | `GET /api/localizations`, `GET /api/localizations/{culture}`, `PUT /api/localizations`, `DELETE /api/localizations/{culture}/{key}`  |
| Изображения      | `GET/POST /api/card-images`, `GET/DELETE /api/card-images/{key}`                                                                     |
| REST-лобби       | `GET/POST /api/lobbies`, `POST /api/lobbies/{id}/join`, `/start`, `/leave`, `/disband`                                               |

REST-лобби существуют на сервере, но текущий клиентский UI использует для
лобби эквивалентные hub-методы, чтобы сразу получать realtime-обновления.

Изображение карты (`GET /api/card-images/{key}`) доступно без токена и может
кэшироваться браузером. Изменение, удаление и загрузка изображения требуют
авторизации.

## Маршрутизация и защита UI

- Анонимный пользователь может находиться только на главной странице с формой
  входа; остальные маршруты перенаправляются на `/`.
- Авторизованный игрок без матча не должен оставаться на `/game`.
- Авторизованный игрок с активным матчем должен быть перенаправлен на `/game`.
- Пока HTTP или требуемый realtime-канал недоступен, UI должен блокировать
  действия и показывать состояние повторного подключения.
