# StateSync: протокол JSON-транспорта, версия 1

Этот документ определяет независимый от языка формат обмена состоянием
`StateSync`. Он описывает только репликацию состояния: аутентификация,
адреса, SignalR/WebSocket/HTTP-фрейминг и игровые команды находятся за его
пределами.

Ключевые слова **ДОЛЖЕН**, **НЕ ДОЛЖЕН**, **СЛЕДУЕТ** используются в
нормативном смысле.

## 1. Модель работы

Сервер является единственным источником истины. Для каждого клиента он может
строить отдельную проекцию состояния (например, скрывать карты соперника).
Клиент получает полный `snapshot`, после чего применяет упорядоченные `patch`.
Клиент не отправляет изменения StateSync обратно серверу.

Версия — неотрицательное целое JSON-число. Начальная версия — `0`. Реализация
сервера не должна выдавать версии больше `9_007_199_254_740_991`
(`Number.MAX_SAFE_INTEGER`), чтобы JavaScript-клиент не потерял точность.

Каждый документ сообщения имеет следующий вид:

```json
{
  "version": 17,
  "state": {}
}
```

или:

```json
{
  "kind": "replaceValue",
  "fromVersion": 17,
  "toVersion": 18,
  "path": "/phase",
  "value": "combat"
}
```

Имена полей чувствительны к регистру. Неизвестные поля клиент может
игнорировать для прямой совместимости, но неизвестный `kind` обязан считать
неподдерживаемым. Тип сообщения определяется RPC-методом или другим внешним
контекстом транспорта.

Один JSON-документ образует одно сообщение. При потоковом транспорте границы
сообщений должны обеспечиваться транспортом (например, WebSocket message,
newline-delimited JSON или SignalR JSON Hub Protocol), а не поиском `}` в
байтовом потоке.

## 2. Snapshot

```json
{
  "version": 42,
  "state": {
    "Phase": "combat",
    "Players": []
  }
}
```

`version` и `state` обязательны. Получив snapshot, клиент **ДОЛЖЕН** полностью
заменить локальное корневое состояние значением `state` и установить текущую
версию в `version`; объединять объекты или списки с прежним состоянием нельзя.
Snapshot допустим при любой текущей версии клиента и является способом
восстановления после рассинхронизации.

## 3. Patch

Общие обязательные поля каждого patch:

| Поле          | Тип            | Значение                                                    |
|---------------|----------------|-------------------------------------------------------------|
| `kind`        | string         | Вид операции из раздела 4.                                  |
| `fromVersion` | integer | Версия, на которой операция должна быть применена.          |
| `toVersion`   | integer | Версия после успешного применения; не меньше `fromVersion`. |
| `path`        | string         | Путь к целевому свойству, списку или значению.              |

Перед применением клиент **ДОЛЖЕН** проверить, что его текущая версия в точности
равна `fromVersion`. После успешного применения он устанавливает
`toVersion`. Patch с несовпадающей версией, неверным путём, неправильным типом
значения или индексом вне границ применять нельзя: клиенту следует запросить
новый snapshot.

В одном ответе или последовательности сообщений patch применяются строго в
порядке доставки. Сервер может разбить одну фактическую смену состояния на
несколько patch с промежуточными версиями. В частности, patch
`fromVersion == toVersion` допустим для обновления видимости и тоже должен быть
применён.

`value`, если он требуется операцией, обязателен даже когда новое значение —
`null`. Поле с отсутствующим `value` и поле `"value": null` не эквивалентны.

## 4. Операции

### `replaceValue`

Заменяет значение свойства по `path` целиком.

```json
{
  "kind": "replaceValue",
  "fromVersion": 42,
  "toVersion": 43,
  "path": "/Players/0/Health",
  "value": 17
}
```

`value` обязателен. Индексные поля отсутствуют. Путь `/` заменяет корневой
объект.

### `insertListItem`

Вставляет `value` перед текущим элементом `index` списка по `path`.

```json
{
  "kind": "insertListItem",
  "fromVersion": 43,
  "toVersion": 44,
  "path": "/Players",
  "index": 1,
  "value": {
    "Id": "f552beb8-b4db-4c90-b4dc-2aa7e6fdf4ec",
    "Health": 20
  }
}
```

Допустимый диапазон: `0 <= index <= длина_списка`; `index == длина_списка`
добавляет элемент в конец. `fromIndex` и `toIndex` отсутствуют.

### `removeListItem`

Удаляет элемент списка по `index`.

```json
{
  "kind": "removeListItem",
  "fromVersion": 44,
  "toVersion": 45,
  "path": "/Players",
  "index": 1
}
```

`value`, `fromIndex` и `toIndex` отсутствуют. Допустимый диапазон:
`0 <= index < длина_списка`.

### `replaceListItem`

Заменяет элемент списка по `index` значением `value`. `value` и `index`
обязательны; `fromIndex` и `toIndex` отсутствуют. Индекс должен существовать.

```json
{
  "kind": "replaceListItem",
  "fromVersion": 45,
  "toVersion": 46,
  "path": "/Players",
  "index": 0,
  "value": {
    "Id": "f552beb8-b4db-4c90-b4dc-2aa7e6fdf4ec",
    "Health": 17
  }
}
```

### `moveListItem`

Перемещает существующий элемент списка. Клиент берёт элемент с `fromIndex`,
удаляет его, затем вставляет в `toIndex` в уже укороченный список.
`fromIndex` и `toIndex` обязательны, `index` и `value` отсутствуют. Оба индекса
должны принадлежать диапазону исходного списка `0 .. длина_списка - 1`.

```json
{
  "kind": "moveListItem",
  "fromVersion": 46,
  "toVersion": 47,
  "path": "/Players",
  "fromIndex": 2,
  "toIndex": 0
}
```

### `clearList`

Очищает список по `path`. `value`, `index`, `fromIndex` и `toIndex`
отсутствуют.

```json
{
  "kind": "clearList",
  "fromVersion": 47,
  "toVersion": 48,
  "path": "/Players"
}
```

## 5. Пути

`path` — строка в синтаксисе JSON Pointer (RFC 6901), начиная с `/`.
Корень обозначается единственной строкой `/`. Сегмент объекта — имя свойства;
сегмент списка — неотрицательный десятичный индекс.

```text
/Players/0/Hand/2/Title
```

означает `state.Players[0].Hand[2].Title`. В имени свойства `~` кодируется как
`~0`, а `/` — как `~1`. При разборе сначала заменяется `~1` на `/`, затем `~0`
на `~`. Пустые сегменты не допускаются; отрицательные индексы не допускаются.

Для `replaceValue` последний сегмент (кроме корня) должен быть свойством. Для
операций над списком `path` должен указывать непосредственно на список.

## 6. Формат `state` и `value`

Схема игрового состояния задаётся моделью конкретной игры и передаётся отдельно
от StateSync. JSON-значения обязаны соответствовать объявленному типу в этой
модели:

- объект модели — JSON object; ключи — точные имена свойств модели;
- `IList<T>` — JSON array;
- строка, bool, числа и `null` передаются нативными JSON-значениями;
- GUID, дата/время и специальные числовые типы должны быть однозначно
  определены контрактом игры. GUID и время рекомендуется передавать строками.
  Enum в стандартном `JsonStatePayloadCodec` передаётся строковым camelCase
  именем (например, `"fast"`), а не числом.

Свойство, скрытое правилами видимости, обычно присутствует со значением `null`;
список может содержать `null` или не содержать скрытый элемент — это является
частью проекции сервера, а не сигналом клиенту восстанавливать исходный список.
Клиент не должен выводить или кэшировать скрытые данные из предыдущих проекций.

Модель StateSync не поддерживает циклы, повторное использование одного
интерфейсного объекта в двух местах, произвольные map/dictionary и массивы;
допускаются простые значения, интерфейсные объекты и `IList<T>`.

## 7. Восстановление и доставка

Протокол не содержит подтверждений, повторной доставки или команды `resync`.
Их организует транспорт/API. Минимальный алгоритм клиента:

1. Получить и применить snapshot.
2. Получать patch в порядке сервера и применять только при точном совпадении
   `fromVersion`.
3. При пропуске, дубликате, неверном patch, переподключении или ошибке разбора
   отбросить локальную копию и получить snapshot.

Snapshot и patch должны относиться к одному аутентифицированному клиенту:
пересылать patch, построенный для другого игрока, недопустимо из-за правил
видимости.

## 8. Соответствие текущей .NET-библиотеке

Серверный StateSync возвращает plain CLR-данные: словари, списки, примитивы,
enum и `null`. SignalR сериализует их один раз общими
`JsonSerializerOptions` с `JsonStringEnumConverter(JsonNamingPolicy.CamelCase)`.
`StateSync.Json.JsonStatePayloadCodec` используется только .NET-клиентом, чтобы
прочитать `state` и `value` в интерфейсные StateSync-прокси. `StatePatch`
предоставляет `path` как строковое JSON-свойство и преобразует его в
`ModelPath` через `Parse`/`ToPathString`. Сами `StateSnapshot<T>` и
`StatePatch<T>` сериализуются обычным механизмом `System.Text.Json`, без
специального конвертера сообщений.
